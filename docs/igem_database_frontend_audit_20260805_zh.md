## 0. 审计结论

本次审计基于只读嵌套仓库：

```text

上游：git@github.com:Yifan-Jia123/igem_database.git
```

上游已经不是单纯线框图，而是一个可运行的 React/Vite + FastAPI + MySQL 原型。其最有价值的资产是：

1. 以化合物为节点、酶/反应关系为边的全屏可交互地图；
2. 重叠边按酶展开、边与酶卡片联动；

最终建议不是抛弃或缩减该方案，而是：

- **保留其数据库页面和交互规划的全部范围**；
- 把当前数据库地图提升为统一产品的 `Atlas` 层；
- 在同一信息架构中增加 `Navigator` 模型工作台、`Evidence` 证据层和 `Campaign` 湿实验闭环；
- 统一两套视觉语言，避免首页“宇宙地图”和内页“浅色企业后台”像两个独立产品。

## 1. 嵌套 Git 管理决策

### 1.1 为什么不直接把上游源码复制进主仓库

主仓库已有明确合同：`external_repos/` 是只读第三方依赖与研究参考区，目录默认被父仓库忽略。把上游源码普通复制进主仓库会造成：

- 上游历史丢失；
- 后续更新无法准确比较；
- 父仓库误提交大量生成依赖；
- 无法证明比赛展示所参考的具体版本。

### 1.2 为什么当前不改成 Git submodule

主仓库现有外部仓库均采用“被忽略的独立 Git 仓库”惯例，并没有 `.gitmodules`。只为一个仓库引入 submodule 会造成两套外部依赖管理方式并存。更重要的是，上游当前追踪了 `frontend/node_modules`、`frontend/dist`、IDE 元数据和 `backend/.env` 路径，直接 submodule 全量检出会带来体积、供应链和配置泄露风险。

因此当前采用：

```text
父仓库跟踪 lock + sync/verify 脚本
        ↓
external_repos/igem_database 保持独立 .git
        ↓
detached HEAD 固定 commit
        ↓
sparse checkout 排除 node_modules
```

对应资产：

```text
reproducibility/external_repos/igem_database.lock.json
scripts/setup/sync_igem_database_reference.sh
```

这不是“随手 clone 后放着不管”，而是一种与主仓库既有合同一致的 pinned nested Git 管理方式。

### 1.3 上游卫生风险

只记录风险，不读取或传播敏感内容：

| 路径类别 | 风险 | 本项目处理 |
|---|---|---|
| `frontend/node_modules` | 上游追踪依赖树，体积与供应链不可控 | sparse checkout 明确排除 |
| `frontend/dist` | 构建产物可能与源码版本、环境不一致 | 仅用于只读预览，不作为我们的实现源 |
| `.idea/` | IDE 本地状态不应成为产品合同 | 不复用 |
| `backend/.env` | 可能包含环境配置或凭据 | 禁止读取、复制、记录或作为主仓库配置来源 |
| `latest` 前端依赖 | 构建不可复现 | 我们正式实现时必须固定 lockfile 与版本策略 |

## 2. 上游技术方案抽取

### 2.1 技术栈

| 层 | 当前上游实现 |
|---|---|
| 前端 | React + TypeScript + Vite + Lucide Icons |
| 图交互 | 自定义 SVG + React 状态 + 自编 force layout |
| 后端 | FastAPI + SQLAlchemy 异步接口 |
| 数据库 | MySQL 8，8 张核心表 |
| 同源检索 | 本地 BLAST 接口设计 |
| 化学图像 | 后端代理 Rhea atom map 与 ChEBI structure SVG |
| 下载 | 后端生成文件；前端另有本地 CSV 队列实现 |

### 2.2 页面结构

当前 `App.tsx` 实际开放的视图：

```text
home       全屏化合物图主页
search     条目搜索列表 + 右侧详情
Downloads  通用下载队列
enzyme     酶详情页
```

代码中还保留一套较传统的 `NetworkView`/Dashboard 组件，但当前 `View` 类型不再暴露该页面。这说明项目经历过一次从“后台式网络页”向“沉浸式地图首页”的切换，旧视觉和旧组件尚未完全收口。

### 2.3 首页地图的真实交互

`CompoundGraphHome` 已实现：

- 首次加载局部 `GraphPayload`；
- 自定义力导布局与碰撞松弛；
- 画布平移；
- 节点拖动；
- 节点拖到视口边缘后按方向扩展邻域；
- 化合物节点选择与相邻关系高亮；
- 化合物对/重叠边选择；
- 调用 `/graph/edge-groups/{id}/edges` 展开重叠边；
- 按 enzyme 聚合展开后的多条 reaction edge；
- 选中边、候选卡片和浮动详情的同步；
- 通路搜索后高亮 compoundIds、edgeIds、edgeGroupIds；
- 本地图搜索建议与后端条目建议融合；
- 找到库外搜索结果后，按酶详情中的底物/产物自动扩图并定位；
- 可拖动的浮动详情面板；
- 节点尺寸、标签尺寸和图控制项。

这部分是上游最值得保留的交互资产。

### 2.4 搜索与详情

当前搜索页已经能：

- 展示 compound、enzyme、reaction 混合结果；
- 按实体类型切换；
- 调用后端条目搜索；
- 对长氨基酸字符串自动尝试同源检索；
- 展示物种、化合物类别、酶家族筛选框；
- 使用“结果列表 + 右侧详情”布局；
- 打开外部记录并加入下载队列。

酶详情页已经有独立实现，并可加载序列、反应、gene、evidence、external links 等 DTO。

### 2.5 API 与 DTO

上游规划和实现采用 `/api/v1`，主要对象包括：

- `CompoundCard`；
- `EnzymeCard`；
- `EnzymeDetail`；
- `ReactionEdge`；
- `EdgeGroup`；
- `GraphPayload`；
- `PathwayCard`；
- `HomologyResult`；
- 下载请求与文件响应。

其最正确的架构原则是：

> 前端传稳定 ID 和筛选条件；后端完成图结构组装、通路计算、生物学业务逻辑和外部 URL 生成，并返回可直接渲染的 DTO。

这个原则应直接继承到统一前端，模型侧也应返回“本次真实路由”和“证据结构”，而不是让前端自行猜测模型行为。

## 5. 实景视觉审计

对固定 commit 的 `frontend/dist` 进行了浏览器实景预览，API 使用受控模拟数据，仅用于检查视觉与交互，不作为科学结果。

### 5.1 首页

视觉特征：

- 紫灰色星图/网格背景；
- 化合物节点使用白色发光圆；
- 选中节点有粉色多层光环；
- 边极细，酶名作为小号文字沿图分布；
- 顶部是大号搜索胶囊；
- 左上数据集胶囊，右侧下载和图控制胶囊；
- 左侧浮出深色化合物详情卡。

优点：

- 第一眼具有比赛演示的沉浸感；
- 地图占据主舞台，符合“从整体到局部”的数据库定位；
- 发光节点和浮层具备明确品牌感。

问题：

- 边和标签太细太小，真实复杂图中难以阅读；
- 来源、审核状态、方向、重叠状态缺少稳定的视觉语法；
- 大量发光会削弱“高亮”的意义；
- 没有明确告诉用户当前是数据库事实还是 AI 候选；
- 低对比文字在投影和比赛大屏上风险较高。

### 5.2 搜索与下载内页

内页采用浅薰衣草色后台式布局：

- 左侧导航；
- 顶部状态与下载操作；
- 大圆角卡片；
- 搜索结果列表 + 右侧详情；
- 颜色区分 compound/enzyme/reaction。

内页清晰、成熟、容易操作，但与首页的暗色宇宙地图形成明显割裂。用户会感觉从一个“科学探索产品”跳到了另一个“管理后台”。

### 5.3 视觉结论

不应简单选择暗色或浅色其中之一。建议统一为同一设计系统的两种场景模式：

```text
Atlas Explore：暗色沉浸地图，强调空间关系和发现
Workbench：浅色高密度工作台，强调表格、证据和操作
```

二者共享字体、颜色语义、圆角、边框、状态 badge、动效时序和顶部运行状态，保证是同一产品的不同工作模式。

## 7. 对统一前端的直接启示

上游数据库前端已经证明“地图作为首页”是可行的，但模型系统不能只作为地图旁的一个按钮。统一产品需要三种互相连接、但不互相吞没的空间：

1. **Atlas**：数据库事实、通路关系和条目检索；
2. **Navigator**：双向开放世界模型的数据流、候选排名和证据；
3. **Campaign**：从候选面板到孔板、QC、七态反馈和下一轮发现。

最重要的连接动作：

```text
数据库反应/酶详情 → Ask Navigator
模型候选 → Open in Atlas
模型候选 → Add to Entry Cart / Pathway Cart
模型候选 → Build Campaign
湿实验阳性/阴性/不确定 → Registry / Next Iteration
```

这套连接关系是下一份总规划的核心。
